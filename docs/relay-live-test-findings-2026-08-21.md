# 真实中转端测试与自动化边界（2026-08-21）

本文记录一次 OpenAI Chat Completions 兼容中转端的实测观察，以及 Relay Model
Auditor 尚不能做到“端点加 Key 后无人值守拉取并验证全部模型”的原因。文中不保存
API Key，也不把中转端指纹当作官方模型真值。

## 本次观察到的 API 特点

- `GET /v1/models` 可用，返回 13 个模型 ID；列表同时包含文本、图片以及
  `*-openai-compact` 变体。模型出现在列表中不代表它支持 Chat Completions，也不代表
  当前 Key 对它有完整采样权限。
- 文本路由总体兼容 `POST /v1/chat/completions`，但 reasoning 控制并不统一。
  `gpt-5.5`、`gpt-5.6-sol`、`gpt-5.6-terra` 接受
  `reasoning.enabled=false`，响应中仍出现正 reasoning token；`gpt-5.6-luna` 则降级到
  post-reasoning 通道。
- 限流是端点级运行条件，而不是单个请求偶发错误。补充 quick 采集即使把并发降到 2，
  后半段仍连续出现 HTTP 429；严格 Luna 批次只有 55/400 个有效样本、345 个错误。
- 指纹属于“模型 + 协议 + 采样计划 + 时间窗口”，不存在一个可以代表整个 API 的单一
  指纹。当前活动 OpenTech 基线只覆盖 4 个同名模型，其余模型只能使用旧快照或没有可比
  基线。
- 本轮严格指纹中，CCTQ 的 Sol/Terra 都更接近各自的 OpenTech 同名参考：

  | 目标 | OpenTech Sol | OpenTech Terra |
  |---|---:|---:|
  | CCTQ Sol | **0.116** | 0.264 |
  | CCTQ Terra | 0.255 | **0.130** |

  但 CCTQ Sol 与 Terra 的直接距离只有 0.210，仍落入旧版低距离带。因此这是一轮相对
  区分信号，不是已经校准的模型身份认证。

其中“13 个模型 ID”和补充 quick 采集在低并发下继续出现 429 属于本次会话观察，原始
`/models` 响应未持久化；严格批次的距离、有效样本数和错误数可由本地证据文件复核。

## 本次测试时为何不能全自动拉取

1. 测试时模型发现直接拼接 `/models`，而采样会把裸域规范化到 `/v1`；同一端点的发现和
   采样可能请求不同路径。发现流程也没有处理 429/5xx 重试、分页或非标准响应结构。
2. Web 工作流只在用户点击后发现模型，之后仍需勾选模型。映射只对完全相同的模型 ID
   自动建议；别名、动态路由和缺失基线无法安全猜测。
3. 浏览器 Key 有意只保存在服务进程内存。刷新页面可以重新关联任务，但服务重启会清除
   Key 并把未完成批次标记为 `interrupted`。
4. 测试时常规 API 虽然接受 `api_key_env` 字段，但缺少安全的白名单、端点绑定和统一解析；直接
   信任调用方给出的环境变量名还可能把服务凭据发送到任意 URL。
5. reasoning adapter 探测和正式采样尚未共享站点级限流状态。429 可能被误判为参数不兼容，
   从而切换 adapter 或降级到 post-reasoning；大量错误样本也可能以 `completed` 结束。
6. 自动测试 `/models` 返回的所有 ID 会引入不可控成本，并可能误测图片、Embedding、无权限
   或非 Chat Completions 模型。自动化必须先生成有请求预算的计划，而不是盲目全选。

## 本次改动覆盖的阻塞点

- 新增环境变量名白名单和运维侧的 `api_key_env -> Base URL` 映射；创建登记与实际执行
  都检查该映射，调用方不能先登记攻击者 URL 再套用已批准的 Key。
- 使用托管 Key 的登记、发现和审计要求本地管理令牌，防止未认证的本机调用方消耗额度；
  这仍不能替代后续的逐模型 allowlist 和请求预算。
- 带凭据的常规审计必须匹配已登记且启用的
  `base_url + model + api_key_env`，阻止把批准的 Key 改送到其他地址。
- 新增 `POST /api/v1/endpoints/{endpoint_id}/models`，允许脚本使用服务端环境凭据拉取已登记
  端点的模型列表，请求体不再携带明文 Key。
- 模型发现与指纹采样统一 Base URL 规范化，并对 429/502/503/504 和短暂网络错误做有界
  重试。
- Smoke、One Token、Tokenizer 的常规 API 都由服务显式解析凭据；One Token 子进程只获得
  当前任务的随机临时变量，不再继承服务进程中的其他供应商 Key。
- 若完整 Key 出现在将被返回或持久化的抽取结果、CLI 输出或证据文件中，任务会 fail
  closed，污染的指纹文件会被删除，Key 不会作为成功结果持久化或返回。
- Compose 默认只绑定 `127.0.0.1`；多用户或远程部署仍必须另加登录鉴权和密钥管理。

## 仍需后续 PR

- 为环境变量凭据批次持久化完整的非秘密运行规格，并在服务启动后重建队列；临时浏览器
  Key 批次继续保持“重启即中断”的安全语义。
- 修正指纹子模块的 adapter 分类：只有明确的 400/422 参数拒绝才切换策略，429、5xx、
  timeout 必须作为 transient 处理。
- 将指纹子模块的网络请求改为不自动跟随 301/302/307/308，防止最终响应来源偏离登记的
  Base URL；父项目中的模型发现、Smoke 和 Tokenizer 已禁止重定向。
- 增加按端点共享的 Retry-After、动态降并发、断路器和最低有效样本门。
- 增加模型 allowlist、请求预算、分页/供应商响应适配，以及别名映射的人工确认计划。
- 用独立的同模型重复批次和已知替换批次校准阈值；在此之前 operational verdict 继续
  fail closed 为 `unverifiable`。
